# SETUP.md — аккаунты, ключи, окружение

Всё, что нужно завести и поставить до первой строчки кода. Аккаунты заводить **в первый день**:
у CDS бывает очередь и ручное подтверждение лицензии, это не делается «когда понадобится».

---

## 1. Аккаунты и креды

| Что | Зачем | Как получить | Где хранится |
|---|---|---|---|
| **GitHub** | репозиторий, CI | есть | — |
| **ECMWF Open Data** | оперативный анализ IFS 0.25° для инициализации Aurora | **ключ не нужен**, публичный доступ | — |
| **AWS Open Data (GFS)** | резервный источник, бакет `noaa-gfs-bdp-pds` | **аккаунт не нужен**, анонимный доступ | — |
| **Copernicus CDS** | ERA5 и ряды в точке | регистрация → страница «How to API» → personal access token | `~/.cdsapirc` (`url:` + `key:`) |
| **Лицензия ERA5** | без неё токен бесполезен | вручную открыть страницу датасета → Terms of Use → Accept | — |
| **ARCO ERA5 (GCS)** | Zarr-архив ERA5 для карт за прошлое | **аккаунт не нужен**, нужен пакет `gcsfs` | — |
| **Hugging Face** | веса Aurora, репозиторий `microsoft/aurora` | токен в профиле HF | `HF_TOKEN` в env |

Типовая ошибка №1 при первом запуске CDS: лицензию **нельзя** принять из API. Если её
не принять руками на сайте, запрос падает с `403 required licences not accepted`.

Ключи — только в `.env` (в `.gitignore`) или в переменных окружения. Никаких токенов
в коде, в конфигах репозитория и в `manifest.json`.

## 2. Лицензии данных — заполнить `LICENSES.md`

| Источник | Лицензия | Требование |
|---|---|---|
| ECMWF Open Data (IFS/AIFS) | CC-BY-4.0 + ECMWF Terms of Use | указание источника в продукте |
| GFS / NOAA | public domain | нет |
| ERA5 / Copernicus | Copernicus licence | указание источника |
| Веса Aurora | лицензия репозитория `microsoft/aurora` | прочитать перед публикацией демо |

Для учебного проекта достаточно строки атрибуции в футере и раздела в README.
Но проверить перед демо надо, потому что права на веса принадлежат провайдеру модели,
а не тому, кто их скачал.

## 3. Железо

| Узел | Роль | Требования |
|---|---|---|
| Сервер проекта | приём, хранилище, кэш, API | диск **300 ГБ**, 16+ ГБ RAM, постоянный аптайм |
| GPU-узел (только на время школы) | инференс Aurora | NVIDIA, **40 ГБ VRAM** для 0.25°, CUDA-драйвер, ~20 ГБ под чекпоинты |
| Ноутбуки разработчиков | разработка, тесты на фикстурах | Docker, ~50 ГБ свободно |

**MacBook / Apple Silicon инференс Aurora не потянет** — нужен CUDA. Разработка конвейера
на маке возможна и нужна (всё, кроме шага «модель»), тесты идут на фикстурах без GPU.

Проверка окружения `make setup` должна показать: `.cdsapirc` читается, ECMWF open data
отвечает, GRIB открывается, `HF_TOKEN` есть, GPU виден (или явно сообщено, что его нет).

## 4. Зависимости

Два **разных** окружения. Не пытаться свести в одно: у torch с CUDA тяжёлые зависимости,
которым нечего делать на сервере API.

### Окружение A — сервис (сервер проекта, ноутбуки)

```
python 3.11–3.12
xarray, numpy, dask[distributed]
zarr >= 3          ← формат v3, шардинг; проверить, что версия действительно 3.x
cfgrib + eccodes   ← бинарная зависимость! ставить из conda-forge, pip-версии ломаются на ARM
ecmwf-opendata     ← скачивание открытых данных ECMWF
herbie-data        ← GFS с публичных зеркал
cdsapi             ← ERA5 и ряды в точке
gcsfs, s3fs, fsspec
pyarrow            ← Parquet для точечных рядов
fastapi, uvicorn, pydantic
apscheduler        ← планировщик цикла
pytest, ruff, mypy, pre-commit
structlog, prometheus-client
```

### Окружение B — инференс (GPU-узел)

```
python 3.11–3.12
torch (сборка под CUDA конкретного узла — уточнить версию драйвера!)
microsoft-aurora
xarray, zarr>=3, numpy
```

Пакет модели ставится **отдельно** и общего venv с сервисом не имеет. Обмен между
окружениями — только через хранилище и очередь, не через импорт кода.
