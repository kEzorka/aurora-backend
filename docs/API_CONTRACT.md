# API_CONTRACT.md

> Документ переписан по `ADDENDUM-01` §4. Главное изменение: полос доступа три, а не одна,
> и часовой шаг в прогнозе теперь настоящий, а не интерполированный.

Все времена в ответах — ISO 8601 с `Z`.

---

## 0. Три полосы доступа

Одна полоса не закрывает три разных запроса: «покажи точку на виджете», «дай мне
подмножество массива в ноутбук» и «выгрузи регион за год». Полосы читают **одно и то же
хранилище**; вторая и третья не копируют данные и не заводят свой формат.

| Полоса | Что | Кому | Приоритет |
|---|---|---|---|
| **1. JSON `/v1`** | компактная укладка сетки, ряды в точке, метаданные | фронтенд | **P0** |
| **2. Zarr `/zarr/`** (xpublish) | тот же Dataset как Zarr-хранилище по HTTP; клиент открывает `xr.open_zarr(url)` и режет сам | питонисты, ноутбуки | P1 |
| **3. Экспорт `POST /v1/export`** | асинхронная задача: NetCDF/Zarr-архив, ссылка по готовности | тяжёлые выгрузки | P1 |

Полоса 1 нужна потому, что 45 байт на точку в наивной укладке убивают виджет.
Полоса 2 — потому что клиенту с xarray JSON только мешает: он всё равно соберёт из него
массив, потратив вдвое больше трафика. Полоса 3 — потому что запрос «регион за год»
не должен держать HTTP-соединение десять минут.

Базовый префикс полосы 1: `/v1`.

## 1. Компактный формат сетки — обязателен

Наивная укладка стоит ~45 байт на точку:

```json
[{"lat": 55.75, "lon": 37.60, "value": 21.3}, {"lat": 55.75, "lon": 37.85, "value": 21.1}]
```

Каноническая укладка стоит ~5 байт на точку — описание сетки плюс плоский массив
в порядке `row-major` (сначала все долготы первой широты, затем второй и так далее):

```json
{
  "grid": {
    "lat0": 56.50, "lon0": 35.50,
    "dlat": -0.25, "dlon": 0.25,
    "shape": [7, 17],
    "order": "row-major"
  },
  "values": [21.3, 21.1, 20.8, null, 20.4]
}
```

На 16 000 точек разница между ~700 КБ и ~90 КБ. Пропуски передаются как `null`,
не как `-9999` и не как `NaN` (невалидный JSON).

Числа округляются, и знаки берутся **от единицы, а не от поля**: 0.1 °C и 0.1 гПа
осмысленны, 0.1 Па — нет, поэтому одно и то же `msl` в `units=si` и `units=human`
округляется по-разному (`api/fields.py`, `_DIGITS`). Без этого `float32` печатается как
`21.340000000000003` — 18 байт вместо пяти, то есть ~290 КБ вместо 90 на том же окне.
Замер на 0.25°: окно 161 × 101 = 16 261 точка весит **77.8 КБ**, 4.8 байта на точку.

## 2. Эндпоинты

### `GET /v1/forecast/point`

Прогноз в точке на 10 суток.

| Параметр | Тип | Обяз. | По умолчанию |
|---|---|---|---|
| `lat`, `lon` | float | да | — |
| `vars` | список | нет | `t2m,wind,msl` |
| `from`, `to` | ISO time | нет | от ближайшего шага до +240 ч |
| `units` | `si` \| `human` | нет | `human` (°C, гПа, м/с) |
| `step_hours` | `1` \| `6` | нет | `6` |

`step_hours=1` работает только на первые **72 часа** от `init_time` и только для восьми
переменных часового слоя (`2t`, `10u`, `10v`, `msl`, `tp_1h`, `tcc`, `2d`, `i10fg`).
Запрос часового шага дальше 72 ч или по другой переменной — `400`, а не молчаливое
округление до шести часов: молчаливое округление даёт пользователю не тот ряд, который
он просил, и он об этом не узнает.

```json
{
  "query": {"lat": 55.75, "lon": 37.62, "nearest_grid": {"lat": 55.75, "lon": 37.50}},
  "source": "aurora-forecast",
  "init_time": "2026-08-01T00:00:00Z",
  "step_hours": 6,
  "units": {"t2m": "degC", "wind_speed": "m/s", "msl": "hPa"},
  "times": ["2026-08-01T06:00:00Z", "2026-08-01T12:00:00Z"],
  "series": {"t2m": [18.4, 24.1], "wind_speed": [3.2, 4.8], "msl": [1012.4, 1011.8]}
}
```

`nearest_grid` возвращается всегда: пользователь должен видеть, что попал в узел сетки
0.25° (≈25 км), а не в свой двор.

### `GET /v1/forecast/grid`

Прогноз по прямоугольнику на один момент.

| Параметр | Тип | Обяз. | Примечание |
|---|---|---|---|
| `bbox` | `south,west,north,east` | да | четыре числа, именно в этом порядке |
| `var` | строка | да | одна переменная за запрос |
| `time` | ISO time | да | округляется к ближайшему шагу 6 ч |
| `stride` | int ≥ 1 | нет | прореживание: берётся каждый `stride`-й узел |

Ответ — блок `grid` + `values` из раздела 1, плюс `source`, `init_time`, `units`.

### `GET /v1/history/point`

Ряд в точке за произвольный период с 1940 года. **Может быть медленным**: при промахе
кэша данные тянутся из внешнего источника.

Параметры как у `forecast/point` плюс `agg` = `raw6h` \| `daily` \| `monthly`.

```json
{
  "source": "era5-final",
  "agg": "daily",
  "cache": {"hit": false, "origin_latency_ms": 4120},
  "times": ["1990-01-01", "1990-01-02"],
  "series": {"t2m_mean": [-8.1, -6.4], "t2m_min": [-12.0, -9.9], "t2m_max": [-4.2, -3.1]}
}
```

### `GET /v1/history/grid`

Карта за прошлое. Те же параметры, что у `forecast/grid`, плюс `agg`.
Часовое разрешение по всей сетке **не поддерживается** — только 6 ч, суточные и месячные
агрегаты (причина — в `STORAGE.md`).

### `GET /v1/meta/coverage`

Что вообще есть: доступные переменные, границы по времени для каждого слоя, `init_time`
последнего прогноза, его возраст в часах. Фронтенд обязан вызывать это при старте,
чтобы не показывать пользователю недоступные периоды.

```json
{
  "source": "aurora-forecast",
  "init_time": "2026-08-01T00:00:00Z",
  "age_hours": 8.3,
  "expected_next": "2026-08-01T06:00:00Z",
  "layers": [
    {
      "step_hours": 1,
      "from": "2026-08-01T01:00:00Z",
      "to": "2026-08-04T00:00:00Z",
      "steps": 72,
      "vars": [{"name": "t2m", "units": {"si": "K", "human": "degC"}}]
    }
  ],
  "limits": {"max_points": 50000, "max_steps": 500, "vars_per_grid": 1}
}
```

Из ответа не должно быть видно хранилища — иначе «не зная деталей» не выполнено:

1. **Слой описан шагом, а не именем.** `coarse`, `hourly` и `points` — слова диска;
   узнав их, фронтенд начинает от них зависеть, и переименование каталога ломает
   интерфейс. Наружу выходит `step_hours`.
2. **Одно публичное имя на величину.** Сервис примет и `2t`, и `t2m`, но рядом в списке
   это две одинаковые температуры. `wind` предлагается, только когда лежат `10u` и `10v`.
3. **Границы читаются с диска, а не из каталога слоёв.** Канон говорит, сколько шагов
   прогон должен был записать; покрытие — сколько записано. Оборванный прогон читатель
   обязан увидеть.
4. **Лимиты в теле.** `stride` фронтенд обязан уметь посчитать заранее, а не узнать
   из `413` (§3).

Полей на уровнях давления в покрытии нет, хотя в слое их 65 из 91: `level` не берут ни
точка, ни сетка, и на `t` обе отвечают `400`. Имя в покрытии — обещание, что его можно
подставить в `vars`; `t` был бы кнопкой, не работающей никогда. Уровни отдаёт полоса 2,
`/zarr/`.

Возраст отдаётся числом, а порога устаревания нет: контракт его не задаёт, и выдуманный
порог в ответе — это решение за того, кто его не принимал. `age_hours` и `expected_next`
позволяют решить самому.

### `GET /v1/health`

Статус: доступность хранилища, свежесть прогноза, заполненность диска, живость воркера.

```json
{
  "status": "ok",
  "storage": {"readable": true, "free_bytes": 121000000000, "total_bytes": 480000000000},
  "forecast": {
    "source": "aurora-forecast",
    "init_time": "2026-08-01T00:00:00Z",
    "age_hours": 8.3,
    "expected_next": "2026-08-01T06:00:00Z",
    "layers": [{"step_hours": 1, "steps": 72}, {"step_hours": 6, "steps": 40}]
  }
}
```

Диск отдаётся файловой системой, а не бюджетами из `STORAGE.md` §3: 40 ГБ ядра и 195 ГБ
кэша — это план, а не разделы, и пока ротация (задача 2.6) их не выдерживает, «кэш
заполнен на 42 %» было бы выдумкой. Живость воркера появится вместе с воркером: описывать
его heartbeat со стороны читателя значит закрепить формат, который писать будет не он.

Прогона нет — `503` со `"status": "no_forecast"` и `Retry-After`, но блок `storage`
остаётся: «хранилище доступно» и «прогноз есть» — разные вопросы, и ответ на первый
не должен пропадать вместе со вторым.

## 2а. Полоса 2 — `/zarr/` (xpublish, P1)

`xpublish` поднимает над тем же `xr.Dataset` эндпоинты Zarr: клиент делает
`xr.open_zarr("https://.../zarr/forecast/current")` и режет массив сам, скачивая только
нужные чанки.

Правила:

1. **Только чтение.** Никаких записей, никакого `POST`.
2. **Раскладка чанков — часть контракта.** Клиент, читающий точку, скачивает целый чанк;
   раскладка A (карта на срок) для точечного запроса означает 4.15 МБ ради 4 байт.
   Поэтому `/zarr/` отдаёт оба варианта раскладки под разными путями (`STORAGE.md` §3),
   а `meta`-документ говорит, какой под какой сценарий.
3. **Лимиты полосы 1 сюда не переносятся** и не могут: клиент сам решает, сколько чанков
   ему скачать. Ограничение — на уровне сети (rate limit по IP), а не на уровне запроса.
4. Манифест прогона отдаётся плагином (`ADDENDUM-01`, задача 5.10, P2): `init_time`,
   версия чекпоинта, отчёт валидации. Без него клиент не отличит один прогон от другого.

## 2б. Полоса 3 — `POST /v1/export` (P1)

Асинхронная выгрузка: запрос создаёт задачу, ответ — `202` и `job_id`.

```json
{"job_id": "exp_01H...", "status": "queued", "poll": "/v1/export/exp_01H..."}
```

`GET /v1/export/{job_id}` возвращает `status` (`queued` / `running` / `ready` / `failed`),
а для готовой — `url` и `expires_at`. Файлы живут в `scratch/` с квотой и чистятся по
`expires_at`; выдача ссылки на исчезнувший файл — это `410`, а не `404`.

Задача обязана содержать те же `source` и `init_time`, что и JSON-ответ: выгрузка без
провенанса через месяц неотличима от чужих данных.

## 3. Лимиты

| Лимит | Значение | Что при превышении |
|---|---|---|
| Точек в одном ответе | **50 000** | `413`, в теле подсказка с нужным `stride` |
| Шагов времени в одном ответе | 500 | `413` |
| Переменных на запрос сетки | 1 | `400` |
| Диапазон истории за один запрос | 100 лет для точки, 1 год для сетки | `413` |
| Одновременных «холодных» запросов к истории | 4 | `429` с `Retry-After` |

Без потолка по точкам первый же запрос «весь мир на все шаги» соберёт 41 миллион чисел
и положит сервис. Потолок — не защита от злоумышленника, а защита от опечатки во фронтенде.

Подсказка в ошибке `413` обязательна и должна быть исполнимой:

```json
{
  "error": "too_many_points",
  "requested": 1038240,
  "limit": 50000,
  "hint": "используйте stride >= 5 или уменьшите bbox",
  "suggested_stride": 5
}
```

«Исполнимая» означает две вещи. Первая: подсказку можно подставить в тот же запрос
и получить `200` — она считается перебором, а не по формуле `sqrt(точек / потолок)`,
которая на узком окне (одна строка, много столбцов) даёт число, при котором точек
всё ещё больше потолка. Вторая: она наименьшая из работающих — на шаг мельче запрос
обязан остаться отказом, иначе сервис молча отнимает разрешение. Считается подсказка
от **неразреженного** окна: пользователь подставляет её вместо своего `stride`,
а не поверх него.

## 4. Коды ответов

| Код | Когда |
|---|---|
| `200` | всё есть |
| `206` | часть периода отдана, часть недоступна (см. поле `gaps`) |
| `400` | кривой `bbox`, неизвестная переменная, `from > to` |
| `404` | дата вне покрытия (например, будущее дальше +240 ч, или до 1940 года) |
| `413` | превышены лимиты объёма |
| `429` | слишком много холодных запросов |
| `503` | внешний источник недоступен, а в кэше данных нет; обязательно `Retry-After` |

## 5. Правила, о которых обычно забывают

1. **Всегда возвращать `source` и `init_time`.** Пользователь должен различать «прогноз,
   посчитанный 8 часов назад» и «реанализ».
2. **Часовой шаг — не интерполяция, и путать их нельзя.** Сроки внутри первых 72 часов
   посчитаны самой моделью (`fine_lead_times`, `DOMAIN.md` §3), поэтому флага
   `interpolated` у них нет. Флаг остаётся для случая, когда значение всё же получено
   вставкой между сроками — например, часовой ряд дальше 72 часов, если он когда-нибудь
   появится. Пометить настоящий прогноз как интерполяцию так же неверно, как обратное.
3. **`era5t` — предварительные данные.** В ответе для дат моложе трёх месяцев указывать
   `"source": "era5t"` и флаг `"preliminary": true`: значения могут измениться задним числом.
4. **Единицы всегда в ответе.** Даже если они «очевидны». Особенно если очевидны.
5. **Кэшируемость:** прогноз меняется 4 раза в сутки — отдавать `Cache-Control` с TTL
   до следующего ожидаемого `init_time`. История старше трёх месяцев неизменна — TTL большой.
