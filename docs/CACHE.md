# CACHE.md — кэш истории и вытеснение

Полный архив ERA5 у нас не помещается (см. `STORAGE.md`). Поэтому история работает как кэш
с внешним origin: если данных нет на диске — тянем из внешнего источника, кладём на диск,
отдаём; когда место кончается — вытесняем то, что дешевле восстановить.

---

## 1. Два origin, и это разные origin

| Тип запроса | Origin | Почему именно он |
|---|---|---|
| **Карта за прошлое** | ARCO ERA5 (публичный Zarr в GCS) | чанкован по одному шагу времени — карта читается за один-два запроса |
| **Ряд в точке за годы** | датасет CDS «ERA5 hourly time-series on single levels» | специально уложен для длинных рядов в одной точке |

Тянуть длинный ряд в точке из ARCO — катастрофа: чанк там равен шагу времени, и 80 лет
по часам это сотни тысяч обращений на один ответ. Ошибка неочевидная, потому что на коротком
периоде при отладке всё работает быстро. Проверять на периоде в десятилетия, а не на неделе.

---

## 2. Термины

**LRU (Least Recently Used)** — стратегия «вытесняем то, к чему дольше всего не обращались».
Работает потому, что у запросов есть локальность: если спросили про Москву, скоро спросят ещё.

**Пиннинг (pin)** — пометка «этот объект вытеснять нельзя». Нужна, потому что прогноз
запрашивают реже, чем популярную историческую точку, и чистый LRU однажды удалит именно его.
Список того, что пиннится, — в `STORAGE.md`, раздел 2.

**Ватермарки** — пороги запуска и остановки чистки: фоновая чистка стартует на **85%**
заполнения и чистит до **70%**. Так чистка не срабатывает в момент записи нового прогона.

---

## 3. Три правила

### 3.1. Кэшируй чанк, а не запрос

Ключ кэша — `(датасет, переменная, версия_источника, индекс_чанка)`. Не «строка запроса».
Иначе два соседних запроса на пересекающиеся периоды положат в кэш два перекрывающихся
куска, и кэш раздуется вдвое при нулевом росте покрытия.

Практически: любой внешний запрос выравнивается по границам чанков origin — просим чуть
больше, чем нужно, зато кладём цельный чанк, который переиспользуется.

### 3.2. Вытесняй с учётом цены восстановления

Чистый LRU здесь неверен. Чанк из ARCO возвращается за ~200 мс, ряд из CDS — за минуты,
потому что там очередь. Первым по чистому LRU вылетит именно дорогое, если к нему давно
не обращались.

Оценка полезности объекта — комбинация трёх величин:

```
score = f(время_с_последнего_доступа, стоимость_восстановления_мс, размер_байт)
```

Вытесняем объекты с наименьшим score. Конкретный вид `f` подобрать по журналу запросов;
на старте достаточно: приоритет удержания у объектов с высокой стоимостью восстановления
и малым размером.

### 3.3. Негативное кэширование

Запрос на дату, которой в ERA5 ещё нет (последние ~5 суток — задержка реанализа), не должен
каждый раз ходить наружу. Отрицательный ответ кэшируется с коротким TTL (6 часов).
Иначе один любопытный пользователь с фронтенда сгенерирует поток бесполезных внешних запросов.

## 4. SQLite: две таблицы, разные задачи

Их часто путают в одну — не надо.

### Таблица `cache_index` — что физически лежит на диске

| Поле | Смысл |
|---|---|
| `key` | `(датасет, переменная, версия, индекс чанка)` |
| `path` | путь на диске |
| `bytes` | размер |
| `last_access` | время последнего обращения |
| `access_count` | сколько раз читали |
| `origin` | `arco` \| `cds` \| `local` |
| `cost_ms` | замеренное время восстановления |
| `pinned` | флаг невытесняемости |
| `source_version` | `era5t` / `era5-final` — нужно для инвалидации |

Без этой таблицы вытеснение невозможно: чтобы отсортировать по времени доступа, нужен
собственный учёт — `atime` файловой системы часто отключён из соображений производительности.

### Таблица `query_log` — что спрашивали пользователи

`ts`, `endpoint`, `bbox` или точка, переменная, диапазон дат, `cache_hit`, `latency_ms`.

Она не участвует в работе кэша. Она нужна для решений: если 80% запросов приходятся
на десяток городов — эти точки надо запиннить и предрассчитать, а не ждать промаха.
Раз в неделю смотреть отчёт `make cache-report`.

**Почему SQLite, а не Postgres или Redis:** один файл, ноль администрирования, транзакции,
режим WAL позволяет писать из воркера и читать из API одновременно. Наши нагрузки — десятки
операций в секунду, запас огромный. Postgres — лишний сервер, который надо поднимать
и сопровождать. Redis держит данные в памяти: при перезапуске индекс потеряется, а файлы
на диске останутся сиротами, и место придётся вычищать вручную.

## 5. Инвалидация

| Событие | Что инвалидировать |
|---|---|
| Новый `init_time` прогноза | все ответы API по прогнозу; сами чанки прогноза — по ротации |
| Приход ERA5T за новые сутки | ничего (это новые данные, не замена) |
| Замена ERA5T финальным ERA5 | все чанки за период с `source_version = era5t` |
| Смена версии адаптера | всё, что записано предыдущей версией — версия входит в ключ |

Версия источника и версия адаптера **входят в ключ кэша**. Тогда инвалидация — это не поиск
и удаление, а просто промах по новому ключу; старое уйдёт само по LRU.

---

## 6. Метрики, которые надо отдавать в `/v1/health`

- заполненность диска по слоям и суммарно;
- hit rate за час и за сутки, отдельно для точечных и карточных запросов;
- средняя и 95-й перцентиль задержки при промахе (это лицо системы для пользователя);
- количество вытеснений за сутки и суммарный объём вытесненного;
- количество отказов origin.

Если hit rate ниже ~50% на устоявшемся трафике — либо кэшируются запросы вместо чанков,
либо чанки origin слишком крупные для наших запросов. Обе причины чинятся, но по-разному.
