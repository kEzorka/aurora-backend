# Weather Backend — комплект проектных документов

Бэкенд погодного сервиса: прогноз на 10 суток моделью **Aurora** (0.25°, шаг 6 часов)
и доступ к историческим данным реанализа **ERA5** с 1940 года. Ответы отдаются в JSON.
Визуализация (карты, гифки) — задача фронтенда, бэкенд отдаёт только данные.

Проект учебный (AIRI Summer School). Из этого следуют два жёстких ограничения,
которые надо держать в голове при каждом решении:

1. **GPU доступен только на время школы.** Поэтому API не должен зависеть от GPU.
   Прогнозы считаются заранее и складываются в хранилище; API читает готовое.
2. **Диск 300 ГБ.** Полный часовой архив ERA5 в него не влезает и не влезет никогда
   (одна переменная за 86 лет — 3.1 ТБ). Архитектура истории построена вокруг этого факта.

## Границы проекта

**Делаем:**
приём оперативного анализа → нормализация к канону → хранение в Zarr v3 →
инференс Aurora на 40 шагов → кэш и вытеснение → JSON API для точки и для сетки →
метрики против базовых уровней → журнал происхождения данных.

**Не делаем** (и не обещаем заказчику):
ассимиляцию наблюдений · дообучение или модификацию Aurora · часовой шаг прогноза
(модель шагает по 6 часов, см. `DOMAIN.md`) · гарантии оперативной надёжности ·
собственную визуализацию · прогноз для точки лучше, чем позволяет сетка 0.25° (~25 км).

## Точки входа (`Makefile`)

Цели фиксируются здесь, чтобы «как это запустить» не было устной традицией.

| Цель | Что делает |
|---|---|
| `make setup` | проверка окружения: ключи, доступность источников, версии, наличие GPU |
| `make ingest-analysis` | скачать и нормализовать последний доступный анализ |
| `make ingest-era5 FROM=.. TO=..` | дозалив истории за период |
| `make forecast INIT=..` | поставить в очередь инференс на указанный `init_time` |
| `make validate` | прогнать валидаторы по последнему записанному срезу |
| `make test` | юнит- и контрактные тесты на фикстурах, без сети |
| `make serve` | поднять API локально |
| `make cache-report` | статистика кэша: занято, hit rate, топ вытеснений |

## Структура репозитория

```
docs/              эти документы
adapters/          по одному на источник (ecmwf_opendata, gfs, era5_arco, era5_cds)
pipeline/          ingest → normalize → store → infer → publish
validators/        проверки из DATA_CONTRACT.md, запускаются отдельно
storage/           работа с Zarr v3, раскладки, rechunk
cache/             индекс кэша, вытеснение, прокси к origin
api/               FastAPI, только чтение из хранилища
tests/fixtures/    настоящие куски GRIB/Zarr, обрезанные до пары ячеек
artifacts/         forecast.zarr + manifest.json + validation.json + report.md
```

Правило про адаптеры: вся грязь источника (порядок осей, единицы, имена переменных,
формат времени) заперта внутри адаптера. Наружу адаптер отдаёт **только** каноническую
форму из `DATA_CONTRACT.md`. Если из адаптера наружу торчит слово «GRIB» — адаптер плохой.
