## 1. Что это за проект

Бэкенд для прогноза погоды на нейросетевой модели **Aurora** (`AuroraV1p5`).
Сервис принимает данные из внешних источников, приводит их к канонической
форме, гоняет модель на GPU, кладёт результат в Zarr и отдаёт наружу тремя
полосами API.

Старый бэкенд на сервере `airi` (`~/aurora-backend`) признан негодным и
переписывается с нуля; его состояние снято в ветку `archive/server-state` —
она нужна только как справка, кода оттуда не переносится.

Требования лежат в двух местах и это одни и те же файлы:

* исходники — `/Users/kezorka/hsse/airi_summer_camp/files/*.md`;
* зеркало в репозитории — `docs/*.md`.

**`ADDENDUM-01` главнее основных документов там, где они расходятся.** Что он
переопределяет:

1. модель — `AuroraV1p5`, срок прогноза передаётся параметром вплоть до 1 часа;
2. 26 приземных + 65 уровневых = **91 поле** на шаг (хранится 90, `insolation`
   считается на лету);
3. VRAM 32 ГБ, бюджет диска под прогноз — 17.4 ГБ;
4. три полосы API: JSON `/v1` (P0), `xpublish /zarr/` (P1), асинхронный
   `POST /v1/export` (P1);
5. виртуальные чанки (Icechunk/VirtualiZarr) — **только** для ECMWF и ERA5,
   никогда для GFS;
6. проверка GRIB на уровне сообщений до `cfgrib` (P0);
7. `earthkit-data` как слой доступа (P1);
8. бенчмарк стратегий сроков 4.7 (P0).

Полные тексты — `docs/ARCHITECTURE.md`, `docs/DOMAIN.md`, `docs/DATA_CONTRACT.md`,
`docs/API_CONTRACT.md`, `docs/STORAGE.md`, `docs/CACHE.md`, `docs/PIPELINE.md`,
`docs/TESTING.md`, `docs/SETUP.md`.

## 3. Как всё запустить

```bash
make venv          # uv venv --python 3.12 .venv + requirements/test-minimal.txt
make lint          # ruff check . && ruff format --check . && mypy .
make test          # pytest (без сети)
make serve         # uvicorn api.app:app --host 127.0.0.1 --port 8000
make cache-report  # состояние кэша: заполненность, hit rate, топ точек
```

Интерпретатор — **`.venv/bin/python`**, системный `python3` без зависимостей.

### 3.1. CI и почему он главный

`.github/workflows/ci.yml`, единственная job `check`, ubuntu-latest, Python 3.12:

```
ruff check .
ruff format --check .
mypy .
pytest -m "not network and not gpu"
```

Ставится **только** `requirements/test-minimal.txt` (плюс `cfgrib` и `eccodes`
отдельной строкой). В нём нет `cdsapi`, `gcsfs`, `earthkit-data`, `torch`,
`aurora`, писателей netCDF. Практическое следствие, которое определяет весь
стиль кода:

> Если функциональность нельзя доказать в этом окружении — она не считается
> сделанной. Поэтому все внешние зависимости импортируются **лениво**, а сеть,
> часы и файловые источники **подставляются параметром**.

Отсюда же выбор `.npz` для чанков кэша (`cache/chunks.py`): писателя netCDF в
окружении нет ни одного.

### 3.2. Проверки границ между пакетами

`tests/test_boundaries.py` — исполняемая версия архитектуры:

| Пакет | Что ему запрещено импортировать |
|---|---|
| `api` | `adapters`, `pipeline`, `torch`, `aurora`, `cfgrib`, `cdsapi` |
| `adapters` | `api`, `storage`, `cache`, `pipeline`, `torch`, `aurora` |
| `cache` | `api`, `pipeline`, `torch`, `aurora` |

`api` **может** импортировать `cache` и `storage`; `cache` **может**
импортировать `adapters` и `storage`. Именно поэтому перевод отказа адаптера
(`NotYetInSourceError`) в отказ кэша (`NotYetError`) живёт в `cache/origins.py`,
а не в адаптере.

### 3.3. Тесты не ходят в сеть

Ни один. Фикстуры нарезаны заранее и лежат в репозитории (< 20 МБ суммарно,
фактически 4.6 МБ). `tests/fixtures/fetch.py` помечен маркером `network` и
запускается руками — это инструмент нарезки фикстур, а не тест.

Известный предел, записанный честно: имена переменных ARCO, имена столбцов CSV
у CDS и раскладка адресов ECMWF Open Data взяты **из документации**, а не
проверены против живых сервисов.

## 4. Карта кода

```
contracts/     канон: имена, единицы, сетка, уровни, слои
adapters/      внешние источники → канонический xr.Dataset

storage/       Zarr v3, публикация, манифест, ротация, чтение
cache/         SQLite-индекс, прокси к origin, вытеснение, отчёт
api/           полоса 1: JSON /v1
pipeline/      склейка цикла: приём, проверка, публикация
bench/, report/, artifacts/
tests/         зеркало структуры пакетов
docs/          требования и решения
```

### 4.1. `contracts/`

* `canon.py` — единственный источник правды про имена полей, единицы, сетку
  (721×1440, 0.25°, широта убывает 90→−90, долгота −180…179.75), уровни
  давления (13 из 37), состав слоёв, `HISTORY_START_YEAR = 1940`,
  `STEP_HOURS = 6`, `FINE_STEP_HOURS = 1`.

### 4.2. `adapters/`

| Файл | Что делает |
|---|---|
| `canonical.py` | приведение к канону: перекладка долготы, поэлементная сверка сетки, единицы, провенанс |
| `ecmwf.py`, `opendata.py`, `index.py`, `fetch.py` | ECMWF Open Data: потоки, адреса, разбор `.index`, байтовые диапазоны, ретраи |
| `gfs.py` | GFS (для отладки без ключей) |
| `plan.py` | что и откуда качать на срок: имена, потоки, `ERA5T_STREAM` |
| `grib.py` | чтение GRIB, проверка на уровне сообщений (1.8) |
| `era5_arco.py` | ERA5 из публичного Zarr в GCS: **карты** за срок, чанк = 1 час |
| `era5_cds.py` | ERA5 из CDS: **ряды в точке**, весь ряд одним файлом |
| `era5_grid.py` | ERA5T-карта `ci` из CDS (1.10) |
| `errors.py` | `AdapterError(field, got, expected)` и `NotYetInSourceError` |

Ключевое различие, из-за которого адаптеров ERA5 два: **нарезка**. ARCO нарезан
по одному сроку — карта читается двумя обращениями, а ряд за 10 лет стоил бы
87 672 обращений. CDS отдаёт весь ряд в точке одним файлом, но карт не отдаёт
вовсе. Отсюда: карты — ARCO, ряды — CDS.

### 4.3. `storage/`

`write.py`, `publish.py`, `manifest.py`, `rotate.py`, `read.py`. Читателю API
интересен `read.py`: `MAX_STEPS = 500`, `MAX_POINTS = 50_000`, `Point`, `Grid`,
`point_series`, `grid_window`, `coverage`, `published_run`, `_stride_under`
(подбор исполнимого `stride` перебором, а не формулой).

### 4.4. `cache/` — здесь идёт текущая работа

| Файл | Что делает |
|---|---|
| `index.py` | SQLite: `cache_index`, `query_log`, `absent`; WAL проверяется при открытии; `Key = (dataset, variable, source_version, adapter_version, chunk)`, разделитель `/`; `ORIGINS = ("arco", "cds", "local")`; `NEGATIVE_TTL_S = 6 ч` |
| `proxy.py` | выравнивание периода по границам чанков, `serve()`, отрицательное кэширование, `Grid`, `Origin` (Protocol), `Served`, `TooManyChunksError`, `NotYetError`, **новое: `cold()`** |
| `origins.py` | живые источники под протокол: `ArcoOrigin` (готов), **`CdsOrigin` (новое)** |
| `chunks.py` | кодек чанка: `encode`/`decode` через `.npz`, `allow_pickle=False` |
| `evict.py` | вытеснение по ватермаркам 85 %→70 %, пиннинг, цена восстановления |
| `report.py` | `make cache-report` |
| **`history.py`** | **новое, не дописано**: чанки → ряд в точке и окно карты |

Устройство кэша целиком описано в `docs/CACHE.md`. Два принципа, которые надо
держать в голове при любой правке:

1. **Кэшируется чанк источника, а не запрос пользователя.** Два пересекающихся
   периода, положенные как запросы, занимают вдвое больше места при том же
   покрытии.
2. **Версия источника входит в ключ.** `era5t` против `era5-final`: один ключ на
   обе версии означал бы, что после замены предварительных данных финальными
   пользователь ещё сутки получает старые числа.

### 4.5. `api/`

| Файл | Что делает |
|---|---|
| `app.py` | `create_app(root)`, ручки `/v1/forecast/point`, `/v1/forecast/grid`, `/v1/meta/coverage`, `/v1/health`; `ApiError`, ETag, `Cache-Control`, перевод `RequestValidationError` в `400` |
| `fields.py` | публичные имена и единицы: `t2m`, `wind`, °C, гПа, мм; `Field.values()`, `Field.compact()` |

Формы ответов и коды — `docs/API_CONTRACT.md`. Оттуда же жёсткие правила:
всегда отдавать `source` и `init_time`; `era5t`-ответ обязан нести
`"preliminary": true`; единицы всегда в ответе; `503` всегда с `Retry-After`.

### 7.2. Принятые решения и их причины

Это самая ценная часть документа: решения приняты после разбора, и переоткрывать
их заново дорого.

**(1) Точка едет внутри имени переменной, а не отдельным полем ключа.**
`cache.index.Key` — это `(dataset, variable, source_version, adapter_version,
chunk)`; места под координату в нём нет, и заводить его нельзя: у карт точки не
бывает вовсе. Поэтому `cache.origins.at_point("2t", 55.76, 37.61)` даёт
`"2t@55.75,37.5"` — с округлением до узла сетки (`era5_cds.snap`) сразу, чтобы
37.61 и 37.62 были одним ключом. Точка положена именно в `variable`, а не в
`dataset`, чтобы `dataset` остался один на все точки: иначе `make cache-report`
через год работы превращается в список координат, которые кто-то когда-то
спросил. Минус у нуля снимается (`-0.0` и `0.0` — один узел).

**(2) Чанк ряда CDS — 365 суток.** Метка `era5t` идёт на весь чанк, а
инвалидация ищет её точным сравнением; при чанке в год замена предварительных
данных финальными выбрасывает **один** чанк из десятилетнего ряда, а не весь
ряд. Это и есть та «резка по границе `FINAL_AFTER`», о которой просит заметка в
`adapters/era5_cds.py:read_series`. Мельче нельзя: у CDS каждый чанк — заявка в
очередь, и месячный чанк дал бы 1200 походов в очередь на столетний запрос.

**(3) Версия источника берётся по КОНЦУ чанка** (`CdsOrigin._ends`), тогда как
`ArcoOrigin` берёт её по началу. Это не рассогласование, а следствие длины
чанка: у ARCO чанк равен одному сроку и разницы нет, а версия годового чанка по
его началу обещала бы финальный ERA5 на 364 днях из 365. В коде это помечено
комментарием — иначе следующий читатель «починит» несоответствие.

**(4) У растущего чанка в версию дописывается дата** — `era5t-20260803`. Пока
конец чанка в будущем, источник каждый день отдаёт на сутки больше, и ключ без
даты означал бы навсегда замороженный обрубок года. Обратная сторона записана
честно: точной инвалидации (`where source_version = 'era5t'`) такие чанки не
видны, их убирает вытеснение.

**(5) Пустой ответ CDS — это `NotYetError`, а не сбой.** Реанализ отстаёт от
календаря на ~5 суток. Разбирается по полям отказа (`field == "csv"`,
`got == "no rows"`), а не по тексту сообщения, и только этот случай: остальные
отказы адаптера настоящие и должны доехать до `503`.

**(6) Агрегация (`raw6h`/`daily`/`monthly`) живёт в API, а не в кэше.** Причина
в порядке операций: `wind` — это `hypot(10u, 10v)`, и склейка составляющих
обязана идти **до** усреднения. Единицы (`scale`/`offset`) коммутируют со
средним, а с `min`/`max` — только при `scale > 0`; все текущие множители
положительны, но это надо отметить комментарием, а не оставлять везением.

**(7) `agg=monthly` для сетки — это `400`, а не `413`.** `413` означает
«запрос слишком велик, уменьшите и повторите», а месячных средних по сетке нет
вовсе, пока не сделан слой 2.5 — уменьшать нечего. А вот `daily` по сетке за
длинный период — честный `413`: у `ArcoOrigin.max_chunks = 48`, суточное
окно — это 24 часовых чанка, и более узкий период работает.

**(8) Счётчик холодных запросов (4 разом, `429`) считает по диску, а не по
индексу.** `cache.proxy.cold()` смотрит, лежат ли файлы чанков, и ничего не
меняет. Через индекс делать нельзя: `hit()` двигает счётчики доступа, по которым
вытеснение решает, что удалять, и второй вызов сделал бы все запросы к истории
вдвое «горячее», чем они были.

**(9) Поля склеиваются по общей оси сроков через `xr.merge(join="outer")`, а не
подставляются друг под друга по индексу.** Растущий чанк, взятый для `10u`
утром, а для `10v` в полдень, отличается длиной на несколько часов — сложенные
по индексу, они соединили бы составляющие ветра за разные сроки.

**(10) Версия ответа — по слабейшему звену.** Один предварительный час в ряду за
десять лет делает предварительным весь ответ: «значения могут измениться задним
числом» верно для всего ряда, если верно хоть для одного его срока
(`API_CONTRACT.md` §5.3).

### 7.3. Что осталось сделать

**Шаг 1 — тесты на `cache/history.py`** (файл `tests/cache/test_history.py`):

* ряд в точке за период, пересекающий два чанка, обрезается ровно по запросу
  (годовой чанк без обрезки вернул бы год на запрос о неделе);
* второй такой же запрос идёт целиком с диска: `hit is True`,
  `origin_latency_ms == 0`, походов в стуб-очередь не прибавилось — это и есть
  «`cache.hit` честный» из критерия приёмки;
* два поля (`10u`, `10v`) с разной длиной растущего чанка склеиваются по сроку,
  а не по индексу;
* окно карты: среднее по двум срокам фикстуры ARCO, `bbox` + `stride`, проверка
  геометрии (`lat0`, `dlat`, `shape`) и значения в конкретном узле — фикстура
  `tests/fixtures/arco.py` кладёт в значение номер узла по долготе плюс 1000 за
  каждый срок, поэтому среднее считается в уме;
* смесь версий: если хоть один чанк периода предварительный, `source` ответа —
  `era5t`.

**Шаг 2 — коммит первой половины.** `feat(cache): serve history from cached
chunks`. Эта половина самодостаточна и мержится отдельно.

**Шаг 3 — `api/history.py`**: перевод из канона в публичный вид.

* разбор `agg` (`raw6h` | `daily` | `monthly`), значение по умолчанию — `raw6h`;
* `bucket(times, values, agg) -> (метки, {"mean": [...], "min": [...], "max": [...]})`.
  **Не добавлять `agg` в `api/fields.py`** — `Field` остаётся про имена и
  единицы; функция получает уже склеенный и переведённый ряд;
* имена ключей ответа — `f"{field.name}_{stat}"` (`t2m_mean`, `t2m_min`,
  `t2m_max`), как в примере контракта;
* метки времени: `raw6h` — полный ISO, `daily` — `1990-01-01`,
  `monthly` — `1990-01`;
* потолок точек для сетки — через `storage.read` (`MAX_POINTS`,
  `TooManyPointsError`, подбор `stride`); чтобы не дублировать подбор,
  `_stride_under` в `storage/read.py` надо сделать публичным.

**Шаг 4 — ручки в `api/app.py`**:

* сигнатура `create_app(root=None, *, history=None)` — **keyword-only**, чтобы
  существующие вызовы `create_app(tmp_path)` в тестах не сломались (проверено:
  все вызовы позиционные);
* `history` — контейнер с долгоживущими origin и соединением к индексу. **Это
  важно**: `ArcoOrigin`, созданный на запрос, переоткрывает архив каждый раз, и
  `REFRESH_AFTER` от этого не спасает (заметка записана в `PROGRESS.md`, пункт
  5.5); тест на это не ловит;
* карта ошибок:
  * `NotYetError`, дата раньше 1940 → `404 out_of_coverage`;
  * `TooManyChunksError`, превышение диапазона или числа шагов → `413`;
  * отказ источника → `503` + `Retry-After: 300`;
  * `agg=monthly` для сетки → `400` (см. решение 7);
  * больше четырёх холодных запросов разом → `429` + `Retry-After`;
* блок `cache: {hit, origin_latency_ms}` в теле — прямо из `Series`/`Window`;
* `"preliminary": true` при `source == "era5t"`;
* `Cache-Control`: для данных старше трёх месяцев TTL большой — история
  неизменна (`API_CONTRACT.md` §5.5).

**Шаг 5 — тесты API** (`tests/api/test_history.py`): холодный запрос,
повторный тёплый, `preliminary`, коды `400`/`404`/`413`/`503`, `429` на пятом
одновременном холодном.

**Шаг 6 — гейт, коммит, PR, зелёный CI.**

```bash
make lint && make test
git commit -m "feat(api): history point and grid over the cache"
gh pr create --base adapters/era5-cds --repo kEzorka/aurora-backend
```

**Шаг 7 — `docs/PROGRESS.md`:** строку 5.5 перевести из «не начато» в описание
сделанного с честным перечислением пределов.

## 8. Известные ограничения и долги

1. **Живых источников не видел никто.** ECMWF Open Data, ARCO и CDS проверены
   на фикстурах и подставных транспортах. Что имена переменных в бакете ARCO,
   имена столбцов CSV у CDS и раскладка адресов Open Data совпадают с
   настоящими, доказывает только документация поставщиков.
2. **Два P0 упираются в GPU** — 4.7 (бенчмарк стратегий сроков) и 4.8 (переход
   на `AuroraV1p5`). Доступа к железу пока не было.
3. **1.9 (`earthkit-data`) недоказуем текущим CI**: пакета нет в
   `test-minimal.txt`. Либо добавлять его в тестовые зависимости, либо
   принимать, что критерий приёмки проверяется руками.
4. **Месячных средних (2.5) нет**, поэтому `agg=monthly` для сетки будет
   отвергаться до её появления.
5. **Инвалидация `era5t` → `era5-final` как процесс не написана.** В ключ версия
   входит, находить чанки по ней умеет `cache.index`, но того, кто это
   регулярно запускает, ещё нет.
6. **Отчёт кэша не показывает вытеснения за сутки и отказы origin** — их не
   пишет `query_log`; придут вместе с метриками эпика 6.
7. **`report.md` по проекту (6.3) не начат**, как и остальная приёмка.
