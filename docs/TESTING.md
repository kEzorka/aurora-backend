# TESTING.md

Ключевая мысль: **код может быть синтаксически правильным и научно неверным.** Обычные
юнит-тесты этого не ловят — всё зелёное, а прогноз сдвинут на 6 часов или температура
в градусах Цельсия там, где ожидались кельвины. Ловят только уровни выше «структуры».

---

## Лестница из семи уровней

| Уровень | Что проверяем | Пример проверки |
|---|---|---|
| **Окружение** | версии, доступность, контрольные суммы | эталонный файл на месте и не изменён; `zarr` действительно 3.x |
| **Структура** | размерности, координаты, типы | широта убывает; форма `(721, 1440)`; все 69 полей на месте |
| **Семантика** | единицы, уровни, времена | `valid_time == init_time + lead_time`; `units` совпадает с каноном |
| **Физика** | диапазоны и инварианты | давление > 0; осадки за интервал ≥ 0; `2t` в 180–340 К |
| **Модель** | качество против базовых уровней | на 24 ч Aurora обыгрывает персистенцию по RMSE |
| **Система** | запись-чтение, перезапуск, память | записанный Zarr открывается заново без потерь; воркер переживает kill −9 |
| **Честность проверки** | независимость эталона | эталон не подогнан под ответ; тестовые даты не участвовали в отладке |

«Семантика» и «Физика» окупаются мгновенно — это ровно четыре ловушки из `DOMAIN.md`,
оформленные как тесты. Их писать первыми, до всякой оптимизации.

## Фикстуры

**Фикстуры делать из настоящих файлов, обрезанных до пары ячеек.** Не из синтетических
массивов: синтетика не воспроизводит те самые ловушки, ради которых тесты и пишутся —
у неё правильный порядок осей, правильные единицы и нет накопленных величин.

Что положить в `tests/fixtures/`:

| Фикстура | Зачем |
|---|---|
| Кусок GRIB от ECMWF, 2 шага, 3 переменные, регион 4×4 | базовый путь адаптера |
| Кусок GRIB от GFS **с долготой 0..360** | проверка перекладки осей |
| Файл с осадками, накопленными от начала прогона | проверка разности шагов |
| Файл с температурой в °C вместо К | проверка, что валидатор ловит единицы |
| Битый файл (обрезанный посередине) | проверка внятного отказа |
| Маленький Zarr в обеих раскладках | тесты чтения и раздувания чтения |

Размер всех фикстур вместе — единицы мегабайт. **Тесты не ходят в сеть.** Ни один.
Если тест требует сети, он не тест, а мониторинг, и живёт отдельно.

## Тесты контрактов

Каждая схема из `DATA_CONTRACT.md` имеет два теста: положительный (валидные данные проходят)
и отрицательный (испорченные — падают с внятным сообщением). Отрицательный важнее:
валидатор, который никогда не срабатывал, скорее всего не работает вовсе.

Проверять текст отказа тоже: он должен называть поле, полученное значение и ожидаемое.

## Тесты API

- лимиты: запрос на 1 038 240 точек возвращает `413` и исполнимую подсказку с `suggested_stride`;
- компактный формат: длина `values` равна произведению `shape`;
- провенанс: в каждом ответе есть `source`, у прогноза есть `init_time`;
- граничные даты: 1939 год → `404`; +11 суток → `404`;
- `bbox` с перепутанным порядком чисел → `400`, а не молча другая область;
- пропуски приходят как `null`, а не как `NaN` (это невалидный JSON и падает у клиента).

## Тест на вменяемость конвейера

Один интеграционный тест, который дороже всех остальных вместе:

> Взять исторический `init_time`, для которого у нас есть ERA5 на 10 суток вперёд.
> Прогнать конвейер целиком. Посчитать RMSE по `2t` против ERA5 на 24 ч.
> Он обязан быть **меньше**, чем RMSE персистенции за те же сутки.

Если это условие не выполняется — где-то в конвейере сдвиг времени, перепутанные оси
или неверные единицы. Модель тут ни при чём, Aurora персистенцию обыгрывает уверенно.
Это первый тест, который надо написать после того, как заработает инференс, и он же —
критерий приёмки всего проекта.

Даты для этого теста выбрать **заранее** и не использовать при отладке. Иначе это уже
не проверка, а подгонка.
