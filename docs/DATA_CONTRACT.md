# DATA_CONTRACT.md — контракты данных

Машиночитаемые схемы входа и выхода каждого шага конвейера. Проверяются **тестами**,
а не на ревью. Если данные не проходят контракт — шаг падает и ничего не публикует.

---

## 1. Каноническая форма

Всё, что покидает адаптер, обязано выглядеть так. Без исключений.

| Свойство | Требование |
|---|---|
| Порядок осей | `(time, level, lat, lon)`; для приземных полей `level` отсутствует |
| Широта | от `+90` до `−90`, **строго убывает**, шаг `0.25`, 721 значение |
| Долгота | от `−180` до `179.75`, **строго возрастает**, шаг `0.25`, 1440 значений |
| Время | UTC, тип `datetime64[ns]`, без таймзонных суффиксов |
| Уровни | гПа, по убыванию давления не сортируем — фиксированный список из `DOMAIN.md` |
| Единицы | СИ, см. таблицу в `DOMAIN.md`, обязательный атрибут `units` у каждой переменной |
| Имена переменных | как у Aurora: `2t`, `10u`, `10v`, `msl`, `t`, `u`, `v`, `q`, `z` |
| Тип данных | `float32` при счёте, `float32` при хранении прогноза, `float16` допустим для истории |
| Пропуски | `NaN`, атрибут `_FillValue` проставлен; «магические» числа вроде `-9999` запрещены |

Отдельно: **GFS отдаёт долготу `0..360`**. Перекладка в `−180..180` с пересортировкой оси —
обязанность адаптера GFS, а не последующих шагов и тем более не API.

---

## 2. Схемы по шагам

Для каждого шага — что на входе, что на выходе. Оформить как JSON Schema в `CONTRACTS/`.

### `raw` → `canonical` (адаптер)

**Вход:** файл источника как есть (GRIB2 / NetCDF / Zarr-срез), плюс метаданные скачивания.
**Выход:** `xarray.Dataset` в канонической форме + обязательные атрибуты:

```json
{
  "source": "ecmwf-opendata-ifs | gfs | era5 | era5t",
  "source_url": "...",
  "retrieved_at": "2026-08-01T07:41:12Z",
  "init_time": "2026-08-01T00:00:00Z",
  "kind": "analysis | forecast | reanalysis",
  "grid": "0.25deg-global",
  "adapter_version": "1.0.3"
}
```

### `canonical` → `store` (запись в Zarr)

**Вход:** канонический Dataset, прошедший валидаторы.
**Выход:** срез в Zarr v3 в обеих раскладках + запись в `manifest.json`.
Запись **атомарна**: пока не записаны все переменные среза, срез не считается опубликованным
(флаг `published` в манифесте выставляется последним).

### `store` → `forecast` (инференс)

**Вход:** ровно два шага анализа: `init_time − 6h` и `init_time`, 18 приземных полей и
65 на уровнях давления, плюс статика из официального pickle (36 полей, `DOMAIN.md` §5).
**Выход:** 40 шагов по 6 ч, 90 полей на шаг, плюс часовой слой на первые 72 часа из
8 переменных; `init_time` в атрибутах, `lead_time` как координата.

### `forecast` → `api` (чтение)

**Вход:** запрос по контракту `API_CONTRACT.md`.
**Выход:** JSON, единицы переведены в пользовательские (°C, гПа, мм), провенанс приложен.

## 3. Провенанс

Каждое значение, которое отдаётся наружу, обязано нести источник. Данные меняются
под пользователем: ERA5T через 2–3 месяца переписывается финальным ERA5, и значение
за одну и ту же дату может измениться. Без провенанса это выглядит как баг сервиса.

Допустимые значения поля `source` в ответе:

| Значение | Смысл |
|---|---|
| `aurora-forecast` | наш прогноз, обязательно вместе с `init_time` |
| `ifs-analysis` | оперативный анализ ECMWF |
| `gfs-analysis` | оперативный анализ GFS (резервный путь) |
| `era5t` | предварительный реанализ, **может измениться** |
| `era5-final` | финальный реанализ |
| `climatology` | месячная норма, не фактическое значение |

Файл `manifest.json` рядом с каждым артефактом:

```json
{
  "artifact": "forecast/2026-08-01T00Z",
  "created_at": "2026-08-01T08:14:03Z",
  "inputs": [
    {"source": "ifs-analysis", "valid_time": "2026-08-01T00:00:00Z",
     "stream": "ifs/0p25/oper", "fields": ["2t", "10u", "..."], "checksum": "sha256:..."},
    {"source": "ifs-analysis", "valid_time": "2026-08-01T00:00:00Z",
     "stream": "aifs-single/0p25/oper", "fields": ["lcc", "mcc", "hcc"], "checksum": "sha256:..."},
    {"source": "era5t", "valid_time": "2026-07-27T00:00:00Z",
     "stream": "reanalysis-era5-single-levels", "fields": ["ci"], "checksum": "sha256:..."}
  ],
  "model": {"name": "aurora", "checkpoint": "aurora-0.25-v1.5", "revision": "..."},
  "steps": 40,
  "timings_sec": {"ingest": 480, "normalize": 190, "inference": 260, "write": 520},
  "degraded": null,
  "validation": "validation.json",
  "published": true
}
```

`inputs[].source` — значение из таблицы выше, а не имя потока скачивания
(`ecmwf-opendata-ifs`): словарь провенанса один на весь сервис, иначе одно и то же
происхождение в ответе API и в манифесте называется по-разному.

`inputs[].stream` — адрес у поставщика, и он обязателен (задача 1.10). Одному
`ifs-analysis` соответствуют два разных потока: `ifs/0p25/oper` и
`aifs-single/0p25/oper`, причём облачности `lcc`/`mcc`/`hcc` в первом нет вовсе
(`ADDENDUM-01` §1). Без потока манифест не отвечает на вопрос, откуда взялось поле.

`inputs[].fields` — что именно приехало этой загрузкой; тоже обязательно. Вход
`era5t` на 27 июля в прогоне за 1 августа без списка полей читается как «весь срез
пятидневной давности», тогда как устарела там одна сплочённость льда `ci`, которой
ECMWF Open Data не публикует. Перенос вперёд честен ровно до тех пор, пока виден:
настоящий срок поля лежит и в манифесте, и в атрибутах переменной (`source`,
`stream`, `valid_time`).

`timings_sec` — ровно четыре ключа: `ingest`, `normalize`, `inference`, `write`.
Пропущенный этап неотличим от мгновенного, а по этим числам считаются метрики
прогона (`BACKLOG.md` 6.2).

`degraded` — прогон посчитан, но хуже обычного; `null`, если всё шло по плану. Ключ есть
всегда: его отсутствие читатель не отличит от манифеста, написанного старым кодом, и
«деградации не было» пришлось бы предполагать ровно там, где предполагать нельзя.

```json
{"reason": "late_input", "waited_for": ["ifs/0p25/oper"], "deadline": "2026-08-01T08:30:00Z"}
```

Отдельным полем, а не выводом из `inputs[].source`. GFS в манифесте бывает по двум
причинам: его выбрали намеренно (отладка без ключей ECMWF) и на него откатились, потому
что ECMWF не успел к `HH + 8:30` (`PIPELINE.md` §2). Алерта заслуживает только вторая, а
по источнику входа они неразличимы. `reason` — из закрытого набора, сегодня в нём одна
запись `late_input`: причина, которую никто не ставит, — это словарь, расходящийся с кодом.

`published` выставляется **последним** действием публикации, поверх уже записанного
манифеста с `false`. Прерванный прогон оставляет `false`, а не полуправду.

### Пропущенный прогон: `skip.json`

Прогона может не быть: источник не отдал данные до дедлайна отката, срез не прошёл
валидаторы, инференс не уложился в дедлайн публикации (`PIPELINE.md` §2). «Пропущенный
прогон — нормальная ситуация, она должна быть видна, а не замаскирована» (§3.5), и
видна она отдельным документом в каталоге прогона:

```json
{
  "artifact": "forecast/2026-08-01T00Z",
  "created_at": "2026-08-01T09:30:00Z",
  "init_time": "2026-08-01T00:00:00Z",
  "reason": "no_input",
  "waited_for": ["ifs/0p25/oper", "gfs/0p25"],
  "deadline": "2026-08-01T09:30:00Z",
  "attempts": 5,
  "skipped": true
}
```

Отдельный документ, а не манифест с пустыми полями: у пропущенного прогона нет ни
входов, ни модели, ни шагов, ни таймингов, и провести его через схему манифеста можно
было бы только сняв с неё проверки формы — то есть разрешив нулевые входы и нулевые
шаги настоящим прогонам тоже.

Флаг называется `skipped`, а не `published: false`. Совпади они, отметка о пропуске
читалась бы как публикация, оборванная на середине, а это другая история: там срез на
диске есть и его нужно дописать или убрать.

`reason` — из закрытого набора `no_input | invalid_input | no_forecast`. Свободный текст
стёр бы разницу между «источник молчит» (ждать) и «валидатор отверг срез» (читать отчёт).
`waited_for` обязателен для `no_input`: «данных нет» без имени потока не говорит, чьих.
`attempts` может быть нулём — это отличает «источник молчал полтора часа» от «не пробовали
вовсе, потому что воркер лежал».

## 4. Валидаторы

Отдельно запускаемые проверки. Каждая даёт **внятный отказ**: какое поле, какое значение,
какое ожидалось. Формулировка «validation failed» без деталей — не принимается на ревью.

### Уровень «сообщения» (только для GRIB, до всех остальных)

- файл читается eccodes и содержит хотя бы одно сообщение (ноль сообщений — это чаще
  всего скачанная HTML-страница с ошибкой);
- число сообщений в файле равно числу двумерных срезов в разобранном Dataset.

Уровень существует потому, что cfgrib молча выбрасывает сообщения, которые не смог
уложить в один Dataset: дубликат по (переменная, уровень, срок) даёт одно поле вместо
двух, без исключения и без предупреждения. Все проверки ниже смотрят уже на результат
разбора и такого не видят.

### Уровень «структура»

- размерности ровно `(1440, 721)` для сетки 0.25°;
- широта монотонно убывает, долгота монотонно возрастает;
- нет дубликатов по времени, шаги идут без пропусков;
- присутствуют все поля набора (90 у прогноза Aurora 1.5), а не «сколько нашлось»;
- шаг по времени один на весь набор и равен 1 ч либо 6 ч: смесь шагов означает, что
  часовой и шестичасовой слои склеились при записи, и любая сумма по времени после
  этого врёт.

### Уровень «семантика»

- у каждой переменной есть `units`, и он совпадает с каноном;
- `valid_time == init_time + lead_time` для всех шагов;
- время в UTC, без таймзонных сдвигов;
- уровни давления совпадают со списком из `DOMAIN.md` поэлементно.

### Уровень «физика»

| Проверка | Диапазон |
|---|---|
| Температура 2 м | 180–340 К |
| Приземное давление | 87 000–108 500 Па |
| Компоненты ветра 10 м | −120…120 м/с |
| Удельная влажность | ≥ 0 и ≤ 0.05 кг/кг |
| Осадки за интервал | ≥ 0 (отрицательные — верный признак, что вычли шаги в неверном порядке) |
| Доля NaN на поле | < 0.1%, кроме полей, где пропуски ожидаемы |

### Уровень «здравый смысл»

- разница соседних шагов по `2t` в одной точке не больше 15 К (иначе перепутаны шаги);
- глобальное среднее `2t` в пределах 283–292 К (ловит перепутанные единицы: если получилось
  около 15 — это °C, а не К);
- поле не полностью константно (ловит битую распаковку).

Результат валидации ложится в `validation.json` рядом с артефактом: список проверок,
статус, значения. Отрицательный результат = срез не публикуется.
