## 1. Что не так с текущим кодом

Текущее содержимое `master` (и рабочая копия на сервере `airi:~/aurora-backend`,
которая под git вообще не была) реализует другую систему, чем описана в проектных
документах:

| Требование документов | Что в коде сейчас |
|---|---|
| Инициализация от оперативного анализа IFS/GFS (`PIPELINE.md` §1) | инициализация из локального архива ERA5 — реанализ, который приходит с задержкой 5 суток и для прогноза непригоден |
| Адаптер на источник, наружу только канон (`DATA_CONTRACT.md` §1) | `era5_store.py` читает NetCDF/Zarr напрямую, канонической формы нет |
| Валидаторы четырёх ловушек как отдельный слой (`DOMAIN.md` §6) | `verify_batch.py` — набор assert'ов внутри одного скрипта, без внятных отказов |
| API `/v1/*` по контракту, компактная укладка сетки (`API_CONTRACT.md`) | `app/api.py` — свой формат, компактной укладки нет, лимитов и кодов ошибок нет |
| Кэш истории с origin, SQLite-индекс, вытеснение (`CACHE.md`) | отсутствует |
| Две раскладки чанков A/B (`STORAGE.md` §3) | одна раскладка |
| Разделение окружений сервис / инференс (`SETUP.md` §4) | один `requirements.txt` с torch |

Это не набор багов, а другая архитектура. Правится переписыванием, а не патчами.

## 2. Что сохраняется

Удалять нельзя — это результаты измерений на настоящих полях, полученные на GPU,
который доступен только на время школы:

- `bench/results/*.json` — `read.json`, `shard_bench.json`, `compress.json`,
  `codec_on_forecast.json`, `zarr3_writepath.json`. Ровно те замеры, которые требует
  `STORAGE.md` §7 («что померить в первую же неделю»);
- `bench/charts/*.png`, `report/` — построенные по ним отчёты;
- `SECURITY.md` — аудит пути раздачи.

Переносится в новый код, а не пишется заново:

- `app/inference.py` + `app/batch_builder.py` — сборка `aurora.Batch` и rollout,
  которые демонстрируемо запускались на V100. Переезжают в `pipeline/infer.py`
  и `pipeline/batch.py` с приведением входа к канонической форме;
- `app/sources/arco.py` (существует только на сервере) — рабочее чтение ARCO ERA5
  из GCS. Переезжает в `adapters/era5_arco.py`.

Состояние сервера до переписывания сохранено в ветке `archive/server-state`
и в `airi:~/aurora-backend-code-2026-08-01.tgz` (165 КБ, только код).

Что в снимок намеренно не попало: `bench/scratch` — 15 ГБ промежуточных хранилищ
от прогонов бенчмарков. Результаты этих прогонов (`bench/results/*.json`) лежат
в `master`, сами промежуточные файлы воспроизводимы и место занимают зря.

## 3. Структура репозитория

По `README.md`, раздел «Структура репозитория» — буквально:

```
docs/              проектные документы + docs/specs/ (этот файл и план)
adapters/          ecmwf_opendata, gfs, era5_arco, era5_cds — по одному на источник
pipeline/          ingest → normalize → store → infer → publish
validators/        проверки из DATA_CONTRACT.md, запускаются отдельно
storage/           Zarr v3, раскладки, rechunk, атомарная публикация, манифесты
cache/             индекс кэша (SQLite), вытеснение, прокси к origin
api/               FastAPI, только чтение
tests/fixtures/    настоящие куски GRIB/Zarr, обрезанные до пары ячеек
artifacts/         forecast.zarr + manifest.json + validation.json + report.md
```

Плюс `Makefile` с целями ровно из `README.md`: `setup`, `ingest-analysis`,
`ingest-era5`, `forecast`, `validate`, `test`, `serve`, `cache-report`.

### Границы модулей

Единственное направление зависимостей — `api → storage/cache`. Проверяется тестом
на импорты: `api/` не должен импортировать ничего из `adapters/`, `pipeline/`,
и тем более `torch`.

| Модуль | Вход | Выход | Не знает про |
|---|---|---|---|
| `adapters/*` | URL/файл источника | `xarray.Dataset` в каноне + атрибуты провенанса | Zarr, API, модель |
| `validators/*` | канонический Dataset | список проверок со статусом и внятным текстом | источники, хранилище |
| `storage/*` | канонический Dataset + метаданные | путь опубликованного среза, `manifest.json` | HTTP, модель |
| `cache/*` | ключ чанка | байты/массив с диска или из origin | формат ответа |
| `api/*` | HTTP-запрос | JSON по `API_CONTRACT.md` | GRIB, модель, torch |
| `pipeline/infer.py` | два шага анализа + статика | 40 шагов прогноза | HTTP, кэш |

## 4. Разделение окружений

Два файла зависимостей вместо одного (`SETUP.md` §4):

- `requirements/service.txt` — xarray, zarr>=3, cfgrib, fastapi, apscheduler,
  gcsfs/s3fs, cdsapi, pyarrow. **Без torch.**
- `requirements/inference.txt` — torch под CUDA конкретного узла, `microsoft-aurora`.

Обмен между окружениями — только через хранилище и очередь в SQLite, не через импорт.

## 5. Бюджет диска — отклонение от спецификации

**Это единственное место, где реальность расходится с документами, и расхождение
существенное.**

`SETUP.md` §3 предполагает выделенный диск 300 ГБ («и это не общий раздел с чужими
данными»). Фактически на `airi` (замер 2026-08-01):

```
/dev/vda2  2.0T  1.7T  215G  89%  /
```

Один раздел на всё, вместе с корнем системы, свободно ~215 ГБ. Из них уже занято:
`~/data` — 55 ГБ (`global.zarr` 50 ГБ, `history_surface.zarr` 3.3 ГБ,
`forecast/` 1.9 ГБ), данные предыдущего backend, которые не трогаем;
`~/aurora-backend` — 28 ГБ, из них 15 ГБ `bench/scratch` и 13 ГБ два venv'а.
`bench/scratch` — очевидный кандидат на освобождение, если места станет мало.

Бюджет `STORAGE.md` §2 (34 pinned + 200 cache + 30 scratch + 10 meta = 274 ГБ)
в 238 ГБ не помещается. Пропорции сохраняем, абсолютные числа урезаем:

| Слой | Спецификация | Принято |
|---|---|---|
| pinned ядро | 34 ГБ | 34 ГБ |
| `cache/*` | 200 ГБ | **110 ГБ** |
| `scratch/` | 30 ГБ | 30 ГБ |
| `meta/` | 10 ГБ | 6 ГБ |
| **итого квота проекта** | 274 ГБ | **180 ГБ** |
| запас до заполнения раздела | — | ~35 ГБ |

Реализация: корень проекта `AURORA_ROOT` (по умолчанию `~/aurora-data`) с явной
квотой в конфиге. Ватермарки `CACHE.md` §2 (85% старт чистки, 70% стоп) считаются
**от квоты кэша (110 ГБ)**, а не от свободного места на разделе. Дополнительно —
аварийный порог по разделу целиком: при `use% >= 95` приём останавливается
(`ARCHITECTURE.md`, таблица деградации), независимо от состояния квоты.

Числа в `storage/budget.py` — одна таблица констант, чтобы при переезде на выделенный
диск менялось одно место.

## 6. Порядок сборки

Порядок продиктован двумя вещами: зависимостями из `BACKLOG.md` и тем, что GPU
доступен ограниченное время.

1. **Скелет**: дерево, `Makefile`, разделённые зависимости, ruff + mypy + pre-commit,
   CI. (`BACKLOG` 0.2)
2. **Канон и валидаторы** — чистые функции, без сети, тестируются сразу. Это четыре
   ловушки `DOMAIN.md` §6 в виде кода. (`BACKLOG` 1.3, 1.4)
3. **Фикстуры** — настоящие куски GRIB, обрезанные; нарезаются на сервере. Без них
   пункты 2 и 4 не проверяемы честно. (`BACKLOG` 0.4)
4. **Адаптер GFS** — ключей не требует, даёт долготу `0..360` и потому сразу проверяет
   вторую ловушку. Затем **ECMWF Open Data**. (`BACKLOG` 1.2, 1.1)
5. **Хранилище**: раскладка A, атомарная публикация, манифесты; затем раскладка B
   с шардингом. (`BACKLOG` 2.1, 2.3, 2.4, 2.2)
6. **Инференс и архив прогонов.** Порт старого кода + очередь. **Сразу после первого
   успешного прогона — сохранить 5–10 прогонов вместе с входами и эталонами ERA5**
   (`PIPELINE.md` §6, `BACKLOG` 4.4). Это единственный необратимый пункт плана:
   всё остальное можно доделать после школы, эти прогоны — нет.

   Проверено 2026-08-01: `airi:~/aurora-backend/outputs/` содержит только
   `registry.db` (20 КБ) — сохранённых прогонов там нет. В `~/data/forecast`
   лежит 1.9 ГБ, что меньше одного полного прогноза (11.5 ГБ), то есть это
   тоже не архив. Задача 4.4 не сделана вовсе.
7. **API** `/v1`: точка, сетка в компактной укладке, лимиты и коды, `meta/coverage`,
   `health`. (`BACKLOG` 5.1–5.4)
8. **Кэш**: SQLite-индекс, прокси с выравниванием по чанкам, вытеснение с пиннингом.
   Затем история в API. (`BACKLOG` 3.1–3.3, 5.5)
9. **Метрики и приёмка**: RMSE с весом по косинусу широты, персистенция,
   климатология, тест на вменяемость конвейера. (`BACKLOG` 4.5, 4.6, 6.1)

Пункт 6 стоит раньше API намеренно, вопреки нумерации эпиков: API читает готовые
файлы и пишется в любой момент, а посчитать прогоны без GPU нельзя.

## 7. Тестирование

По `TESTING.md`: семь уровней, ни один тест не ходит в сеть, фикстуры — настоящие
файлы, обрезанные до пары ячеек, суммарно < 20 МБ.

Отрицательные тесты контрактов важнее положительных: проверяется не только факт
отказа, но и текст — он обязан называть поле, полученное значение и ожидаемое.

Критерий приёмки всего проекта — один интеграционный тест: RMSE Aurora по `2t`
на 24 ч меньше RMSE персистенции, на датах, выбранных заранее и не использованных
при отладке.

## 8. Ветки и история

- `master` — не трогаем, force-push запрещён;
- `archive/server-state` — состояние сервера на 2026-08-01 до переписывания,
  включая файлы, которых никогда не было в GitHub (`app/sources/*`, `read_api.py`,
  `map_store.py`, `publish.py`, `contracts.py`);
- `rewrite` — новый backend; вливается в `master` после того, как проходит
  `make test` и тест на вменяемость конвейера.

## 9. Явные допущения

1. Квота диска 180 ГБ вместо 300 ГБ (раздел 5). Если появится выделенный диск —
   меняются константы в `storage/budget.py`, архитектура не меняется.
2. `~/data/*` на сервере считается занятым местом и не переиспользуется:
   `global.zarr` записан предыдущим кодом, его провенанс не документирован,
   а `DATA_CONTRACT.md` §3 требует провенанс для всего, что отдаётся наружу.
   Как источник эталонов для верификации он допустим после отдельной проверки
   валидаторами — но не как слой хранилища.
3. Срок доступности GPU неизвестен и считается коротким. Отсюда порядок в разделе 6.
4. Дообучение и модификация Aurora не делаются (`README.md`, «Не делаем»).
