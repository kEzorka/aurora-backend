Что мы принимаем, что возвращаем и почему это быстро

Три вопроса связаны в один: асинхронность, форма запросов и раскладка данных на диске. Ответ на первый определяет второй, второй определяет третий. Все числа здесь — из замеров на 4×V100, а не оценки.

1. Асинхронность: одна поправка к постановке

Поправка

«Максимизировать число пользователей и уменьшить время ответа» — это две разные задачи, и асинхронность решает только первую. Асинхронность не ускоряет счёт на GPU ни на процент. Шаг прогноза — 2,65 с, он занимает карту целиком, и никакой async его не делит.

Разложим по полочкам, что чем лечится. Числа — из тёплого запроса к сервису (15,8 с на 4 шага, модель уже в памяти карты).

ПроблемаЧем лечитсяПотолок выигрыша
HTTP-поток блокируется на время счётаочередь + опрос статусауже сделано
Чтение архива и запись результата стоят в очереди со счётомasync I/O, перекрытие стадий2,8 с из 15,8 = 18%
Один пользователь ждёт 15,8 спредпосчёт: запрос превращается в чтение15,8 с → миллисекунды
Четверо пользователей одновременно4 воркера на 4 картыбез замедления, замерено
Восемь одновременноочередь перед воркерамибез очереди — OOM у 7 из 8

То есть асинхронность даёт максимум 18% — это стадии read (1,2 с) и write (1,6 с), которые можно перекрыть счётом следующего запроса. Остальные 13 с — forward, и он последователен по определению.

Настоящий ответ на «уменьшить время ответа» другой, и он же снимает противоречие, о котором говорил ментор. Погодный API почти никогда не считает прогноз в момент запроса. Новые данные анализа приходят раз в 6 часов; по ним считается один прогон на 10 суток вперёд и пишется в хранилище. Запрос пользователя после этого — чтение с диска. Инференс становится фоновым производителем, а не обработчиком запросов.

2,65 сшаг forward, не делится
18%потолок от async I/O
4пользователей = карт
~0 мсесли прогноз уже посчитан

Тогда оба требования выполняются одновременно, потому что они перестают конкурировать: время ответа определяется скоростью чтения, а число одновременных пользователей — пропускной способностью диска и сети, а не количеством карт. Карты нужны ровно четырём прогонам в сутки.

2. Архитектура: производитель и читатель — это разные вещи

Практическое следствие для кода: процесс API и процесс инференса — разные процессы. Сейчас в app/jobs.py это один процесс с фоновым потоком, и для прототипа так правильно. Но воркер держит 19 GiB на карте и падает по OOM при перегрузке — API при этом падать не должен.

3. Контракт: два типа запросов

Оба возвращают одно и то же по форме, различаются только тем, откуда взяты данные: история — из архива анализа, прогноз — из посчитанного прогона. Общее у них: список переменных, область и формат ответа.

3.2 История

GET /v1/history?variables=t2m&start=2026-05-01T00&end=2026-05-07T00&lat=55.75&lon=37.62

Период целиком в прошлом и уже лежит в архиве. Никакого GPU, никакой очереди — только чтение. start и end включительно, шаг сетки времени — 6 часов (00, 06, 12, 18 UTC); step=12h прореживает, промежуточные моменты не интерполируются.

{
  // ответ: 200 OK
  "kind": "history",
  "source": "ERA5 reanalysis",
  "point": {"lat": 55.75, "lon": 37.5},     // узел сетки, а не запрошенная точка
  "times": ["2026-05-01T00:00Z", "2026-05-01T06:00Z", "..."],
  "variables": {
    "t2m": {"units": "K", "values": [279.4, 281.1, ...]}
  },
  "meta": {"grid": "0.25deg", "requested": {"lat": 55.75, "lon": 37.62}}
}

3.3 Прогноз — две формы адресации

Ментор прав, что нужны обе, и они отвечают на разные вопросы. Первая — «что модель, запущенная тогда-то, говорит про через столько-то часов»; это форма для сравнения прогонов и для оценки качества. Вторая — «какая погода будет в четверг»; это форма для пользователя, которому всё равно, откуда взялся ответ.

GET /v1/forecast?variables=t2m&init_time=2026-05-01T00&lead_time=24h&lat=55.75&lon=37.62

GET /v1/forecast?variables=t2m&valid_time=2026-05-02T00&lat=55.75&lon=37.62

ПараметрЗначение
init_timeмомент запуска модели, кратен 6 ч
lead_time24h · PT24H · 0-240h для диапазона. Кратно 6 ч, максимум 240 ч
valid_timeмомент, на который нужен прогноз. Взаимоисключающ с парой выше
init_policyкак выбрать прогон для valid_time: latest (по умолчанию) · nearest

Правило разрешения — его надо зафиксировать в документации, а не оставить на усмотрение

При valid_time без init_time берётся самый свежий готовый прогон, у которого init_time ≤ valid_time и есть шаг ровно на valid_time. Ответ всегда сообщает, какой прогон был выбран: без этого клиент не сможет ни воспроизвести запрос, ни понять, почему ответ изменился между двумя вызовами.

{
  // ответ: 200 OK
  "kind": "forecast",
  "init_time": "2026-05-01T18:00Z",   // выбран сервером по valid_time
  "lead_hours": 6,                    // valid_time - init_time
  "valid_time": "2026-05-02T00:00Z",
  "model": "AuroraPretrained",
  "point": {"lat": 55.75, "lon": 37.5},
  "variables": {"t2m": {"units": "K", "values": [281.9]}},
  "meta": {"init_policy": "latest", "produced_at": "2026-05-01T18:41Z"}
}

3.4 Промах кэша: 200 против 202

Если прогон с нужным init_time не посчитан, вернуть пустой ответ нельзя, а ждать 15,8 с внутри HTTP-запроса — плохо. Поэтому у ручки два успешных исхода, и клиент должен уметь различать их по коду:

4. Чанки: почему это не деталь реализации

Замерено, а не предположено

Запрос «температура в одной точке за весь архив» сейчас читает 1442 МБ, чтобы вернуть 1,4 КБ. Коэффициент лишнего — около миллиона. Это не медленный диск и не плохой код: это форма чанка, не совпадающая с формой запроса.

Чанк — минимальная единица чтения. Прочитать половину чанка нельзя: он лежит сжатым, его распаковывают целиком. Сейчас архив нарезан по картам: чанк t2m — это (1 момент, 721, 1440) = 4,15 МБ. Для модели это идеально: ей нужна карта целиком, и она получает её одним чтением. Для точки — катастрофа: чтобы собрать 364 значения в одной точке, нужно распаковать 364 чанка по 4,15 МБ.

Правило: форма чанка должна повторять форму запроса. Два разных вида запросов — два разных правильных ответа, и одна раскладка не может быть обоими сразу.

РаскладкаЧанкРазмерКарта целикомРяд в точке
по картам (сейчас)(1, 721, 1440)4,15 МБ1 чанк364 чанка = 1442 МБ
по времени (предлагается добавить)(1460 моментов, 32, 32)6,0 МБ1035 чанков1–2 чанка за год

Вторая раскладка — копия того же массива, а не замена первой. Цена: ещё 50 ГБ на диске (свободно 1,2 ТБ) и перестроение при каждом пополнении архива. Выигрыш на запросах в точке — примерно тысячекратный, и именно эти запросы будут массовыми у пользователей.

Ориентир по размеру чанка: 1–16 МБ в сжатом виде. Мельче — накладные расходы на метаданные и тысячи мелких чтений; крупнее — обратно та же проблема, что сейчас: читаем много, отдаём мало. Тайл 32×32 по всем 364 моментам архива даёт 1,49 МБ.

Здесь есть ловушка, в которую легко попасть: взять по времени «всё, что есть». Сегодня это 364 момента и 1,49 МБ, но архив растёт — три месяца дали 364 момента, год даст ~1460, два года выведут чанк за верхнюю границу диапазона, и раскладка тихо испортится сама. Поэтому размер по времени фиксируется явно: 1460 моментов, то есть один год на чанк (6,0 МБ), и новый год открывает новые чанки, а не раздувает старые.

5. Горячее и холодное хранение

Это то, о чём говорил ментор, и это не про чанки, а про то, где лежат данные. Два измерения независимы: можно положить данные в самую быструю память и всё равно читать 1442 МБ ради 1,4 КБ, если чанки нарезаны неправильно.

Приятная новость: горячий слой на этой машине уже существует и ничего не стоит. В боксе 251 ГБ RAM, из них 167 ГБ прямо сейчас занято страничным кэшем — Linux сам держит недавно прочитанные файлы в памяти. Отдельный Redis или in-memory-хранилище для начала не нужен; нужно лишь, чтобы горячие данные помещались и чтобы их не вытесняло чем попало.

Отсюда арифметика вытеснения, и она жёсткая. Один прогон на 10 суток — это 744 МБ на сутки прогноза × 10 = 7,4 ГБ. Четыре прогона в сутки — 30 ГБ в день, около 900 ГБ в месяц при 1,2 ТБ свободных. Без политики удаления диск кончится за 40 дней.

ПравилоЗачем
Горячий слой — последние 2 прогона и 7 суток историипокрывает подавляющее большинство запросов: «сейчас» и «ближайшие дни»
После каждого прогона — прочитать новые файлы насквозьпрогрев: иначе первый пользователь платит за холодное чтение

Последняя строка — важная асимметрия. ~/data/global.zarr строился 18 минут, стоил квоту CDS и невоспроизводим в принципе; прогноз на 10 суток пересчитывается за ~130 с на одной карте и ни от чего внешнего не зависит. Дело не в объёме — 7,4 ГБ на прогон при 1,2 ТБ свободных не решают ничего. Хранить надо то, что нельзя получить заново, а не то, что занимает место.

6. Порядок внедрения

Это последовательность: каждый следующий пункт опирается на предыдущий и без него не имеет смысла.

  1. /v1/meta и /v1/history — чистое чтение из ERA5Store, без GPU и без очереди. Даёт рабочую половину контракта за наименьшую цену и сразу проверяет формат ответа на реальных пользователях.
  2. Выбор переменных и точки/bbox в существующем /forecast. Убирает выдачу целых файлов там, где нужен один ряд.
  3. Планировщик: прогон по расписанию раз в 6 ч, запись в хранилище прогнозов. С этого момента /v1/forecast в большинстве случаев отвечает 200, а не 202, и время ответа падает с 15,8 с до чтения.
  4. Вторая раскладка чанков под запросы в точке. Имеет смысл только когда есть кому её читать — то есть после пунктов 1–3.
  5. Политика вытеснения и прогрев. Обязателен к сроку «40 дней от запуска планировщика», а не «когда-нибудь».

Числа: 2,65 с на шаг, 15,8 с тёплый запрос, 19,0 GiB пик, 1442 МБ на ряд в точке, 744 МБ на сутки прогноза — из bench/results/*.json (scripts/bench_suite.py). 251 ГБ RAM, 167 ГБ страничного кэша, 1,2 ТБ свободно — free -g и df -h на машине. Покрытие архива 2026-04-01 … 2026-06-30, 364 момента — из самого global.zarr. Оценка ~130 с на прогон 10 суток — это 40 шагов × (2,65 с forward + 0,24 с выгрузка на CPU + 0,38 с запись) плюс 1,2 с чтения; из них 106 с — собственно счёт.
